## Specs

Each spec quotes the reviewer finding (claim text) and states the required behaviour. User-facing messages are Spanish (tú form, like existing messages).

- S1 [R3-stream-transport-errors-unwrapped, R4-001 part] Finding: "responder only translates openai.APIConnectionError and openai.APIError into ErrorLLM. A transport failure while the stream is already being iterated, for example LM Studio closing or unloading the model mid-answer, can surface as a raw httpx exception. That breaks the ErrorLLM-only contract stated in app/llm/base.py." Required: `ClienteLocal.responder` (app/llm/local_client.py) raises `ErrorLLM` for any failure during the request or while iterating the stream (openai errors and `httpx.HTTPError`, including `RemoteProtocolError`/`ReadTimeout`), with the message exactly: "Se perdió la conexión con el modelo local mientras respondía. Revisa que LM Studio u Ollama siga abierto e inténtalo de nuevo." for failures after streaming started. Test: fake server that sends some chunks then breaks the stream → ErrorLLM with that message, and the fragments yielded before it are still delivered.
- S2 [R3-turn-save-not-atomic] Finding: "The two writes for a turn run in separate SQLite transactions: crear_conversacion first, then agregar_mensajes. If the second write fails ... an empty titled conversation stays in the sidebar list." Required: add `Historial.guardar_turno(conversacion_id: int | None, titulo: str, mensajes: list[Mensaje]) -> int` that creates the conversation (when id is None) and inserts the messages in ONE transaction and returns the id; `Conversacion.enviar` uses it. Test: a failure while inserting messages (e.g. invalid role violating the CHECK) leaves no conversation and no messages (listar_conversaciones() == []).
- S3 [R3-ui-only-catches-errorllm, R4-001] Finding: "The _responder worker catches only ErrorLLM. Any other exception, such as sqlite3 errors from the history or httpx errors from the stream, leaves the bubble showing the thinking ellipsis or partial text with no user-visible error, and the exception escapes the thread." Required: `PantallaChat._responder` (app/ui/chat.py) also catches any other `Exception`: logs it with `logging.exception`, shows in the answer bubble in red: "Ocurrió un error inesperado: <detalle>" (keeping any partial text above it is fine), resets busy state. After a successful turn `conversacion_id` is adopted from the Conversacion; on failure it is unchanged.
- S4 [R3-settings-save-oserror, R4-002] Finding: "_guardar calls guardar_config without handling OSError ... On failure the dialog stays open with no feedback, a leftover .json.tmp file may remain, and the exception escapes the click handler." / "On Windows, os.replace raises PermissionError when another process holds the target open". Required: `guardar_config` (app/config.py) removes the `.json.tmp` file if writing or replacing fails, then re-raises `OSError`. `DialogoAjustes._guardar` catches `OSError`, keeps the dialog open, does not call `al_guardar`, and shows in red in the dialog status text: "No pude guardar los ajustes: <detalle>". Tests: guardar_config failing on replace leaves no .tmp and the previous config.json untouched; dialog shows the message and does not apply settings.
- S5 [R3-blocking-network-on-ui-loop, R4-003] Finding: "Several handlers run synchronous network calls on the UI event loop: the reconnect inside the async _enviar handler, plus _conectar in iniciar and _ajustes_guardados, and listar_modelos in the settings dialog. Each uses ClienteLocal's default 120-second timeout ... freezes the whole window for up to the timeout." Required: `listar_modelos`/`conectar` use a short timeout (5 seconds, constant `TIMEOUT_MODELOS = 5.0` in local_client.py); chat streaming keeps its long timeout. The reconnect in `_enviar`, `iniciar`, `_ajustes_guardados` and the dialog's model loading run off the UI loop via `page.run_thread`, showing a pending state ("Conectando…" in the model label / dialog status) and keeping the busy guard so a second send is not queued meanwhile.
- S6 [R3-repeated-offline-error-bubbles, R4-003 part] Finding: "Each failed reconnect from _enviar, and each failed reconnect after saving settings, appends another red error bubble to the current conversation view." Required: at most one connection-error bubble is shown at a time: a new connection error replaces the previous connection-error bubble instead of appending; a successful connection removes it.
- S7 [R1-001] Finding: "On Linux, the per-user data folder is created with mkdir(parents=True, exist_ok=True) and no explicit mode ... A tighter mode (0o700 for the folder) would limit exposure of user conversations." Required: on non-Windows platforms `carpeta_datos()` ensures the folder mode is 0o700 (os.chmod after mkdir). Windows unchanged. Test (skipped on Windows): folder mode is 0o700.
- S8 [R3-ui-logic-untested] Finding: "No automated test covers the screen logic in app/ui/ajustes.py or app/ui/chat.py. Unproved behaviors include: Save disabled when the provider has no models or is offline, resolver_modelo preselecting the saved model, the busy guard on new/open/settings, and the swap of conversacion_id after a turn." Required: new tests (tests/test_ui.py) driving `PantallaChat` and `DialogoAjustes` through a fake page object (update/show_dialog/pop_dialog/run_thread that runs the function immediately) and fake LLM/servers (no real LM Studio, isolated tmp data dir via EVA_DATA_DIR or explicit paths). Cover those four behaviours plus S3, S4, S6.
